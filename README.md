# 見積・受注前処理エージェント

Lesson 3で採用した構成に沿った、見積・受注前処理エージェントのデモ用MVPです。ローカル開発と、非公開GitHubリポジトリからRender Web Service／Render PostgreSQLへ展開する構成に対応します。公開環境の作成自体は行っていません。

デモ用の入力、期待結果、9分の進行台本、想定質問は [docs/demo-scenarios-2026-09-05.md](docs/demo-scenarios-2026-09-05.md) を参照してください。3ケースの統合検証は `npm run verify:demo-scenarios` で実行できます（起動中のローカルMVPとDBを使用し、Geminiへは送信しません）。

- UI: ブラウザ
- バックエンド: Node.js HTTP API
- DB: PostgreSQL（ローカルではLesson 4専用領域、公開時は`DATABASE_URL`でRender PostgreSQL）
- AI: Gemini API（モデルは`.env`またはRender環境変数の`GEMINI_MODEL`で指定。未設定・障害時もローカル経路を使用可能）
- 認証: サーバー側の1ユーザー認証、DBセッション、HttpOnly Cookie
- データ: 教材配布の原本CSV 5ファイルをバイト列のまま保持し、別テーブル・検索索引へ変換

## 起動

```bash
cd /Users/shohei/work/Codex/2026-07-31/lesson4-mvp
npm install
npm run db:start
npm run db:load
npm run auth:hash-password
npm run dev
```

`npm run auth:hash-password`で作ったハッシュと、32文字以上のランダムなセッション秘密鍵を`.env`へ設定してから起動します。平文パスワード、ハッシュ、秘密鍵はGitへ登録しません。ブラウザで `http://127.0.0.1:4173` を開き、設定したデモユーザーでログインします。

公開準備の設定、環境変数、DB投入、停止・破棄手順は[公開デモ準備ガイド](docs/deployment-readiness.md)を参照してください。Render向けの構成案は`render.yaml`にあります。外部サービスの作成、GitHubへのpush、Geminiへの実送信は、利用者の承認を得てから行ってください。

## 確認項目

1. 環境ステータスでUI・バックエンド・DBを確認
2. 読込件数が顧客200、商品200、過去見積2,000、見積依頼1,000、外注先86であることを確認
3. 任意レコード検索を実行
4. DB書込み・読出し確認を実行
5. AI接続テストを実行

実APIを確認する場合は `.env` に `AI_PROVIDER=gemini`、`GEMINI_API_KEY`、
`GEMINI_MODEL`に接続確認済みのモデルIDを設定します。APIキーは画面やソースコードへ書かず、
業務データは接続テストへ送らないでください。

### 1回限定のAI診断

現在の接続テストは、サーバー側で固定文「接続確認です。日本語でOKとだけ答えてください。」
だけを送ります。自動再試行はなく、待機上限は30秒です。HTTP番号、Googleの状態・エラー本文、
送信回数、所要時間を表示します。エラー本文からAPIキーなどを除き、応答全体やヘッダーは出力しません。
キー設定の存在だけでは、AIの接続を「確認済み」にしません。

サーバーを再起動せず、同じ設定・診断処理で1回だけ確認する場合は以下を実行します。
実APIを呼び、利用枠を消費する可能性があるため、連続実行しないでください。

```bash
node scripts/diagnose-ai.mjs
```

診断処理や画面の変更をブラウザ操作へ反映するには、実行中のサーバーをControl+Cで停止し、
`npm run dev`で再起動してからブラウザを再読み込みします。再起動自体はGeminiを呼びません。

## 原本と変換データ

- `data/raw/`: 教材配布フォルダの原本CSVをバイト単位で複製したもの。BOM・改行コード・末尾空欄を含めて保持し、内容を加工しません。
- PostgreSQLの `*_raw`: 値を文字列のまま保持する原本テーブル。
- `entity_search`: 表記揺れ・全角半角・記号を検索用に正規化した別索引。
- `data/processed/import-summary.json`: 読込件数と品質課題の集計。

この分離により、教材が指示する「元データをきれいにして上書きしない」を守っています。

「練習用の匿名サンプル」を選択して「抽出する」を押してください。

- 実業務データの利用、図面送信、顧客送信、価格確定は行わないでください。

## 統合ワークフロー（Chapter 7）

画面上部の「統合ワークフロー」で、見積依頼入力、情報抽出、人間の原文照合、名寄せ・類似案件、人間の候補判断、承認要否判定、文面下書き、人間の文面判断を一連の流れとして確認できます。安全上必要な人間確認を飛ばす一括自動実行ではありません。

初回だけ、起動済みDBへ機能間の受け渡し版・検索IDを記録する項目を追加します。既存CSVと既存処理記録は変更しません。

```bash
npm run db:prepare-workflow
```

- 次の操作：現在の状態に応じて、利用者が次に行う操作と該当箇所を表示
- 受け渡し：抽出版、類似検索ID、承認判定IDを保存し、古い抽出版の検索結果を後工程で使わない
- 結果：抽出値、上位類似案件と根拠・差異、承認結果と理由、メール下書きを1か所で再表示
- ログ：実行日時、入力要約、抽出結果、上位類似案件、承認結果・理由、生成文面、人間判断を既存のDB記録から時系列表示
- 安全境界：統合表示自体は外部AIを呼ばず、価格・納期の確定とメール自動送信をしない
