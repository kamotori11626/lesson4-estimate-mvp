# 見積・受注前処理エージェント

製造業の見積依頼を題材に、依頼文の情報抽出、顧客・商品の名寄せ、類似見積の検索、承認要否の候補判定、確認メールの下書き作成までを一つにつないだWebアプリです。

TECH::CAMPのFDE模擬実習で作成した学習用MVPであり、実在企業の本番システムではありません。教材で与えられた不完全なデータと業務制約を前提に、AI・ルールベース処理・人間確認をどう分担するかを設計し、ローカル開発とGitHubリポジトリからRenderへ展開できる構成にしました。

## 解決しようとした課題

- 見積依頼の自由文から、顧客名、品番、数量、材質、寸法、公差、希望納期などを整理する負担が大きい
- 顧客名・品番の表記揺れにより、過去見積を探しにくい
- 過去価格を条件差を見ずに転用すると、値付けを誤るおそれがある
- 粗利率、技術確認、外注見積など複数の条件が重なると、確認先が分かりにくい
- 顧客・社内向け文面は必要だが、価格や納期をAIに確約させてはいけない

このMVPは最終判断を自動化しません。候補・根拠・差異・不足情報を表示し、営業、技術担当、管理職などの人間が確認した結果を記録する支援ツールです。

## 主な機能

1. 見積依頼情報の抽出と不足・曖昧情報の検知
2. 顧客・商品の名寄せ候補提示
3. 類似する過去見積の検索と、一致根拠・条件差の表示
4. 価格差のルールベース警告
5. 粗利率、値引き、技術確認、外注見積による承認要否候補の判定
6. 匿名化したAI支援またはローカル定型文によるメール下書き
7. 人間による修正、採否、根拠、保留解消状態の記録
8. 処理結果と監査ログの統合表示

## 本人の担当とAI支援の範囲

|区分|内容|
|---|---|
|本人が行ったこと|教材・配布データの分析、MVP範囲の決定、業務フローと人間確認箇所の設計、承認・価格差ルールの判断、セキュリティ条件の整理、テストケースと合否基準の決定、画面・DB保存・公開環境の確認、メンターフィードバックを受けた修正判断|
|AIを利用したこと|実装案、コードとテストコードの作成支援、調査・デバッグの補助、設計記録とREADMEの文章整理|
|AIに任せていないこと|価格・納期の確定、加工可否、承認、顧客への送信、曖昧な入力の推測確定|

AIが生成した内容をそのまま採用せず、要求事項、配布データ、画面表示、DB保存結果、自動テストと照合して修正しています。

## 構成と使用技術

```text
ブラウザ（HTML / CSS / JavaScript）
        ↓ HTTP API
Node.js
        ↓
PostgreSQL
        ├─ 配布CSV由来の模擬データ
        ├─ 抽出・名寄せ・承認・下書き
        └─ 人間の判断と監査ログ

Gemini API（任意）
  └─ 匿名化プレビューを人間が確認し、その都度同意した場合のみ使用
```

- フロントエンド: HTML / CSS / Vanilla JavaScript
- バックエンド: Node.js HTTP API
- データベース: PostgreSQL
- AI連携: Gemini API（ローカル処理へ切替可能）
- 認証: scryptパスワードハッシュ、DBセッション、HttpOnly Cookie
- テスト: Node.js標準テストランナー
- デプロイ構成: Render Web Service / Render PostgreSQL

## 既知の制約

- 1依頼1商品に限定し、複数商品・商品数不明は保留する
- 商品マスタに加工種別がないため、過去実績から候補を提示し、人間が確認できない場合は技術担当へ回す
- 粗利率18%未満と20%未満という資料間の矛盾を解消せず、18%以上20%未満は保留する
- 値引率の正式閾値と顧客別例外は未決定のため、値引き案件を自動承認しない
- 過去価格の単価・総額、通貨、税区分が十分に定義されていないデータは、そのまま転用しない
- Geminiへ送れるのは許可された匿名サンプルだけで、自由入力、実顧客情報、価格、図面は送らない
- メールは下書きまでで、自動送信機能は実装していない
- 教材配布の模擬データを使用しており、実業務での精度・運用負荷・ROIは未検証

### 1回限定のAI診断

現在の接続テストは、サーバー側で固定文「接続確認です。日本語でOKとだけ答えてください。」

サーバーを再起動せず、同じ設定・診断処理で1回だけ確認する場合は以下を実行します。


## 原本と変換データ

- `data/raw/`: 教材配布フォルダの原本CSVをバイト単位で複製したもの。BOM・改行コード・末尾空欄を含めて保持し、内容を加工しません。
- PostgreSQLの `*_raw`: 値を文字列のまま保持する原本テーブル。
- `entity_search`: 表記揺れ・全角半角・記号を検索用に正規化した別索引。
- `data/processed/import-summary.json`: 読込件数と品質課題の集計。

この分離により、教材が指示する「元データをきれいにして上書きしない」を守っています。
