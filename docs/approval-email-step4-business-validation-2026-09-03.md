# 承認要否判定・メール案作成 Step 4 業務観点検証

検証日: 2026-09-03

## 結論

MVPとしては**条件付き合格**とする。

- Lesson 3で定めた責任境界（ルールエンジンが判定候補を提示し、人間が最終承認・送信する）と一致する。
- 未確認・不足・未定義・ルール競合を安全側の「保留」にする。
- 顧客向け不足情報確認メールと社内確認メールは、通常画面で作成でき、機械的な品質検査に合格した。
- 価格断定、納期確約、自動送信は確認した文面・画面・実装にない。
- ただし、粗利率18%／20%の承認基準の矛盾と、値引率の正式閾値が未決定である。現行判定は正式ルールではなく `approval-rules-0.1-draft` による暫定判定である。

## 参照したLesson 3成果物

- Google Drive上の「役割分担表.txt」
  - Step 13は承認要否・承認経路をルールエンジンが判定する。
  - 粗利率18%／20%の矛盾を解消した単一の最新版ルールを用いることを求めている。
  - 競合・欠損時は、より厳しい経路または判定保留とする。
- Google Drive上の「AIに任せない判断一覧.txt」
  - 価格・値引きの最終決定は営業、承認対象は管理職が行う。

  - AIは候補提示まで、ルールエンジンは判定までで、確定・承認・送信は人間が行う。

## 1. 承認判定とLesson 3ルールの整合

| 確認内容 | 結果 | 根拠 |
|---|---|---|
| 承認要否をルールベースで判定する | 合格 | `src/approval-rules.mjs` の固定ルールでサーバー側再計算・判定する。AIは判定しない。 |
| 未確認の抽出結果を後工程へ通さない | 合格 | 通常画面で未保存の抽出結果に `REVIEW-001` が適用され「保留」になった。 |
| 不足情報を後工程へ通さない | 合格 | 通常画面で品番・材質・寸法・公差の4項目不足に `DATA-001` が適用され「保留」になった。 |
| 粗利率の境界値を安全側で扱う | 暫定合格 | 自動テストで18%未満は承認要、18%以上20%未満は保留、20%以上は粗利率単独のトリガーなしとなった。正式基準ではない。 |
| 値引率の未決定ルールを安全側で扱う | 暫定合格 | 0%はトリガーなし、0%超は正式閾値決定まで保留となった。 |
| 技術・外注確認の必要性を経路へ反映する | 合格 | 根拠入力を必須とし、技術担当または購買・外注担当を確認先として返す。 |
| 判定結果を正式承認と誤認させない | 合格 | 画面に「暫定ルールによる支援」「正式承認ではない」と表示する。 |
| 競合・欠損を安全側で扱う | 合格 | `hold` を `required` より優先し、未解決条件が残る間は後工程を停止する。 |

### 通常画面で確認した代表ケース

- サンプル: 「不足あり（ログ RFQ-00001 参考）」
- 予定見積金額: 10,000円
- 原価: 7,000円
- 値引き前の基準価格: 10,000円
- 再計算結果: 粗利率30%、値引率0%
- 判定: 保留
- 判定理由: 抽出結果の原文照合・修正下書きが未保存、かつ未確定項目が4件
- 判定ID: `d254999b-101e-40ec-b6fd-7705109761cb`
- ルール版: `approval-rules-0.1-draft`

粗利率だけならトリガーなしだが、未確認・不足情報があるため全体を保留にする結果であり、Lesson 3の安全側の責任境界と一致する。

## 2. メール案のビジネス文面としての適切性

### 顧客への不足情報確認

| 観点 | 結果 | 確認内容 |
|---|---|---|
| 件名 | 合格 | `【確認のお願い】PPSカバー80のお見積りについて` と表示され、目的と対象商品が分かる。 |
| 宛名・名乗り | 条件付き合格 | 顧客名、ご担当者様、自社担当者を含む。実送信時は顧客担当者名と正式署名の補完が必要である。 |
| 案件識別 | 合格 | 対象商品、弊社案件番号、顧客が認識できる元メール件名を併記する。 |
| 不足情報 | 合格 | 品番、材質、寸法、公差の4項目を漏れなく列挙する。 |
| 顧客への依頼 | 合格 | 顧客に確認・回答を依頼する一文を明記する。 |
| 回答後の自社対応 | 合格 | 回答確認後に正式な見積金額と納期を改めて連絡すると明記する。 |
| 長さ・敬語 | 合格 | 短く、依頼目的と回答してほしい内容が読み取りやすい。 |
| そのまま使えるか | 条件付き合格 | 元メールへの返信なら本文はほぼそのまま使用可能。新規メールでは宛先、担当者名、正式署名を営業が補う必要がある。 |

### 社内への確認依頼

| 観点 | 結果 | 確認内容 |
|---|---|---|
| 件名 | 合格 | 案件番号と商品名を含み、社内で検索・照合しやすい。 |
| 確認事項 | 合格 | 未確定4項目と追加質問「図面公差の適用可否」を列挙する。 |
| 責任境界 | 合格 | 価格・納期・承認要否は未確定と明記し、確認根拠と判断結果の記録を求める。 |
| 文面の自然さ | 合格 | 社内宛先を `技術担当の方へ`、`購買・外注担当の方へ`、`管理職の方へ` と役割別に表示し、`担当者 ご担当者様` の重複を解消した。 |
| そのまま使えるか | 条件付き合格 | 担当者名が分かる場合は宛名を差し替える程度で利用できる。 |

## 3. 禁止表現と自動送信の確認

| 禁止・制約 | 結果 | 確認内容 |
|---|---|---|
| 価格断定 | 検出なし | `○円で提供します`、`単価を確定しました` 等を含まない。 |
| 納期確約 | 検出なし | `○日に納品します`、`出荷できます` 等を含まない。 |
| 未確認の承認済み表現 | 検出なし | 承認済み・承認完了を創作しない。 |
| 未確認の製造可否・添付 | 検出なし | 製造可能、添付済み等を創作しない。 |
| 顧客文面への社内情報混入 | 検出なし | 粗利率、原価、承認閾値、値引率を顧客メールに含めない。 |
| 自動送信 | なし | 画面に送信ボタンはなく、サービスも送信先APIを返さない。下書き作成と人間による採否記録までである。 |

`「正式な見積金額および納期を改めてご連絡いたします」` は、価格や納期そのものを断定・確約する文ではなく、確認後に連絡するという手続の案内であるため許容する。

## 残る業務課題

1. 業務責任者が、粗利率18%／20%の矛盾を解消し、単一の正式閾値を承認する。
2. 値引率の正式閾値、顧客別例外、承認者を決める。
3. 実際の営業担当者が、担当者名・正式署名・宛先を入れた状態で顧客向け文面を確認する。
4. 実際の担当者名・部署名が利用できる将来版では、役割宛名から個人名・部署名へ差し替える。
5. 利用者認証が未実装のため、採用・承認・送信ログの本人性は担保できない。正式運用前に認証と権限管理が必要である。
