# 類似案件検索・名寄せ支援 Step 1 要件整理

作成日：2026-09-01

## 1. 確認した根拠

- TECH::MASTER「類似案件検索・名寄せ支援」（curriculum 15328）の全本文
- `共通入出力仕様.txt` の入力仕様、`similar_quotes`、操作記録、エラー時動作
- `MVPスコープ定義書.txt` の Step 5・6、対象案件、責任境界
- Chapter 3で実装済みの `extraction-1.0` 出力スキーマ
- 配布原本CSV：`19_顧客マスタ.csv`、`20_商品マスタ.csv`、`18_過去見積履歴.csv`

この機能の目的は、過去価格を自動採用することではない。営業が「候補・一致根拠・今回との差異」を比較し、参照する過去見積を選択または却下できる状態を作ることである。

## 2. 今回決めるMVP方式

### 採用方式

ローカルPostgreSQL上で、次の二段階検索を行う。

1. 顧客・商品の名寄せ候補を提示し、人間が対象を選択する。
2. 選択された顧客・商品と、今回の数量・材質を使って過去見積を検索する。

検索は、文字列の正規化、文字列類似度、キーワード一致、ルールによる重み付けを組み合わせる。MVPではベクトル検索と外部LLMを使用しない。理由は、データが構造化されており、表記ゆれの中心が法人格、旧表記、ハイフン・アンダースコア・空白だからである。検索処理をローカルに閉じれば、顧客名・価格・粗利等を外部AIへ送信せずに済み、同じ入力とデータ版から同じ順位を再現できる。

### 人間の責任境界

- システム：候補、順位、スコア内訳、差異、注意事項を表示する。
- 営業：顧客・商品候補と参照する過去見積を選択または却下し、理由を記録する。
- 必要時の技術見積：仕様差、加工条件、図面・材質等を確認する。
- システムは顧客、商品、過去価格、今回価格、納期、加工可否を自動確定しない。

## 3. 入力要件

### Chapter 3の出力から検索に使う項目

| 項目 | 用途 | 使用条件 |
|---|---|---|
| `request_id` | 全検索・選択・監査記録の共通キー | 必須 |
| `schema_version` | 入出力版の不一致を検知 | `extraction-1.0` と一致しない場合は停止 |
| `case_type` | MVP対象かを判定 | 規格品・類似品だけ検索。新規特注・緊急は手動運用 |
| `item_scope` | 1依頼1商品制限を確認 | `single` だけ検索。複数商品・商品数不明は保留 |
| `customer_name` | 顧客マスタ候補の検索、過去見積の顧客一致 | 人間が確認・修正した現在値を使用 |
| `product_code` | 商品マスタ・過去見積の最重要キー | 人間確認値を優先。欠損時は品名から商品候補を探すが、自動補完しない |
| `product_name` | 品番欠損時の候補検索、商品候補の説明 | 人間が確認・修正した現在値を使用 |
| `material` | 同一・類似品の条件比較 | 欠損時も検索は可能だが、候補ごとに「材質未確認」を表示 |
| `quantity` / `quantity_unit` | 数量差の比較 | 数量欠損時も検索は可能だが、順位精度低下を警告 |
| `dimensions` / `tolerance` | 人間が仕様差を判断するための注意事項 | 過去見積CSVに対応カラムがないため、検索得点には使わない。比較不能を明示 |
| `requested_delivery_date` | 今回の依頼条件表示 | 過去見積CSVに確約納期カラムがないため、検索得点や納期判断には使わない |

### 検索開始条件

- 抽出候補の生値ではなく、画面上で営業が確認・修正した現在値を使う。
- `customer_name` と、`product_code` または `product_name` のどちらかが必要である。
- `multiple`、`out_of_scope`、商品数未確認、規格品・類似品以外は検索せず、手動運用へ戻す。
- 商品候補が複数残る場合、過去見積検索へ進む前に人間の選択を必須とする。

## 4. 検索対象と使用カラム

### 顧客マスタ（200行）

検索：`customer_name`、`billing_name`。候補表示：`customer_id`、`customer_name`、`billing_name`、`delivery_site`、`sales_rep`。支払条件・特別値引・信用ランクは、名寄せの根拠には使わず、必要な権限がある画面でのみ参照する。

実データには200件のIDに対して顧客名が45種類しかなく、多数の重複・表記ゆれがある。顧客名一致だけで1レコードに自動確定しない。

### 商品マスタ（200行）

検索：`品番`、`商品名`、`材質`。候補表示：`product_id`、`品番`、`商品名`、`材質`、`単位`、`廃番フラグ`、`備考`。

実データは完全一致品番40種類、記号と旧表記を除いた論理品番16種類で、200行すべてが重複グループに属する。さらに材質欠損が30行ある。したがって、品番の記号除去一致は候補グループの抽出に使うが、商品レコードの自動統合・自動確定には使わない。廃番・旧表記は明示し、現行候補を上位にするが、人間が確認する。

### 過去見積履歴（2,000行）

検索：`customer_name`、`product_code`、`material`、`quantity`、`quote_date`。候補表示・差異確認：`quote_no`、`quote_date`、`customer_name`、`product_code`、`material`、`process_type`、`quantity`、`quote_price`、`gross_margin_rate`、`approved_by`、`approval_reason`、`note`、`drawing_link`。

全2,000行に品番はあるが、材質欠損が643行ある。対象期間は2023-01-01〜2025-09-26である。材質欠損を一致扱いにせず「比較不能」と表示する。`drawing_link` は `drive://...` 形式のため、MVPでは内部参照値として表示し、Webリンクとして有効だと仮定しない。

## 5. 正規化・名寄せルール

### 顧客名

- Unicode NFKC、前後空白、大小文字、全角半角を統一する。
- 先頭の `旧：`、`旧:`、`旧-` は旧表記フラグとして分離する。
- `株式会社`、`（株）`、`(株)`、`有限会社`、`Co.,Ltd.` 等の法人格は比較用文字列から除外するが、表示値は原本のまま保持する。
- 工場・営業所等の拠点名は勝手に削除しない。別拠点の可能性があるため差異として表示する。

### 品番

- Unicode NFKC、大小文字を統一し、比較用にハイフン、アンダースコア、空白を除去する。
- 先頭の `旧：`、`旧:`、`旧-` は旧表記フラグとして分離する。
- 末尾の型式記号（例：`-A`）や数値は削除しない。`ALBKT22` と `ALBKT22A` は別候補として扱う。
- 商品名・材質は、品番が欠損または候補が複数の場合の補助情報とする。

## 6. 候補順位の暫定ルール

### 顧客・商品候補

- 正規化後の完全一致を最優先する。
- 完全一致が複数行ある場合は統合せず、現行／旧表記、材質、単位、拠点等の差異付きで最大3候補を提示する。
- 文字列類似度は候補漏れを防ぐために使い、類似度だけで確定しない。
- 該当なし、または弱い候補しかない場合は「該当なし／要確認」とする。

### 過去見積候補

人間が選択した商品候補を基準に、最大5件を提示する。スコアは0〜100の説明可能なルール値とし、AIの信頼度とは呼ばない。

| 判定要素 | 点数 |
|---|---:|
| 論理品番が完全一致 | 40 |
| 論理品番は不一致だが文字列類似候補 | 最大18（必ず要確認表示） |
| 顧客の正規化名が一致 | 20 |
| 材質が一致 | 15 |
| 数量が完全一致 | 10 |
| 数量比が0.5〜2.0倍の範囲 | 5 |
| 今回と過去の加工種別が一致 | 10 |
| データ基準日から1年以内 | 5 |
| データ基準日から1年超2年以内 | 3 |

- 品番一致は他条件より重くする。
- 加工種別は任意入力とし、未入力時は0点として「技術確認必要」を表示する。
- 材質欠損は0点であり、不一致とは断定せず「比較不能」とする。
- 現在の見積価格は未確定なので、過去の`quote_price`は参考値として表示するだけで、スコアには使わない。
- 配布CSVには`quote_price`が単価か総額か、通貨、税区分の定義がない。金額は原値として表示し、これらを「未定義」と併記する。
- 価格差異は、同一の顧客・論理品番・材質・数量・加工種別で、正の金額と見積日がある候補だけを比較する。比較可能な候補が2件未満なら「比較不能」とし、価格転用を停止する。
- 比較基準は比較可能候補のうち見積日が最も新しい案件とし、`|比較対象金額 - 基準金額| / 基準金額 × 100`で差率を求める。
- 数値閾値は、10%未満＝通常、10%以上20%未満＝注意、20%以上30%未満＝警告、30%以上＝停止とする。
- ただし重要注記を優先する。「材料・原価の変動」「緊急・短納期条件」は数値判定から1段階繰り上げ、「特別価格・顧客別条件」は最低でも警告、「今回・前回限りの条件」は停止とする。分類できない注記も最低限「注意」として人間が確認する。
- 警告には基準見積・比較見積、差額、基準比、該当注記、確認事項、担当者の次の行動を含める。AIは価格の正誤を判断しない。
- 同点は、論理品番完全一致、顧客一致、見積日の新しい順、`quote_no`順で安定して並べる。

## 7. 出力要件

共通入出力仕様の `similar_quotes` を、次の固定構造として扱う。

| 項目 | 型・内容 |
|---|---|
| `quote_id` | 文字列。過去見積の`quote_no` |
| `similarity_score` | 0〜100の数値。上記ルールの合計 |
| `match_basis` | 配列。各要素に比較項目、今回値、過去値、一致種別、加点、説明を持つ |
| `differences` | 配列。数量、材質、品番、顧客、加工種別、過去見積日、過去価格、仕様比較不能項目を表示する。過去見積日・過去価格は`reference_only`と明示 |
| `source_link` | `drawing_link`等の参照値。無効形式・欠損はnullまたは内部参照として表示 |
| `data_as_of` | 検索に使った固定データスナップショットの日時。候補自身の`quote_date`とは分ける |

候補選択後は、既存の `selected_quote_result` に、採用／却下、理由、確認者、確認時刻を保存する。未選択、候補ゼロ、重大差分時は空欄を許容する。

名寄せ候補は最終成果の新しいトップレベルキーにせず、専用の内部APIスキーマと監査イベントとして固定する。これにより、共通出力のトップレベル構造を無断変更せず、候補提示・選択履歴を保存できる。

## 8. 品質基準

### 技術的な合格条件

1. 完全一致：完全一致の顧客名・品番で、正しい論理グループが1位になる。
2. 表記ゆれ：法人格、旧表記、ハイフン、アンダースコアの差があっても、正しい論理グループが上位3件に入る。
3. 該当なし：未知の顧客・品番を既存データとして自動確定せず、「該当なし／要確認」を返す。
4. 複数候補：類似する過去見積を最大5件、根拠・差異・注意事項付きで返す。
5. 不足耐性：材質・数量・過去見積の承認情報が欠損してもJSON形式を崩さず、比較不能・不足を明示する。
6. 再現性：同じ入力、同じルール版、同じデータスナップショットでは同じ順位になる。
7. 責任境界：候補を自動採用せず、人間が採用・却下理由を保存できる。
8. セキュリティ：顧客名、過去価格、粗利率、図面参照を外部AIへ送信しない。

### テストセットと数値基準

最低12ケース（完全一致3、表記ゆれ3、該当なし3、複数候補3）を用意する。

- 完全一致：正しい論理グループのTop 1率 100%（3/3）。
- 表記ゆれ：正しい論理グループのTop 3率 100%（3/3）。
- 該当なし：誤った自動確定 0件（0/3）。
- 複数候補：営業または技術見積が事前に正解とした候補がTop 3に1件以上入る率 100%（3/3）。
- 全12ケースで、各候補に`match_basis`、`differences`、データ日付、選択要否が表示される。

ただし、過去見積の「業務上の正解」はデータだけから自動定義できない。正解ラベルは営業または技術見積が、品番だけでなく材質・数量・加工条件・旧表記を確認して決める。システム開発者だけで正解を作ると、同じロジックを自分で採点する循環評価になる。

## 9. 保留・エラー時の動作

- 入力版不一致、複数商品、対象外案件、商品候補未選択、DB読込失敗、出力スキーマ不一致、ログ保存失敗は後工程へ渡さない。
- 0件の場合は条件を勝手に緩めて価格候補を出さず、「該当なし」と手動検索への切替を表示する。
- 候補が多い場合も最上位を自動採用せず、最大件数を超えたことと追加絞込条件を表示する。
- 材質、寸法、公差、加工条件の比較ができない場合は、価格転用不可の警告を表示する。
- 再実行は元の監査記録に関連付け、新しい実行IDで保存し、以前の候補・選択履歴を上書きしない。

## 10. 正解ラベルの扱い

本課題には実在する営業・技術担当者がいない。2026-09-02のユーザー確認により、原本確認に基づく模擬営業・技術担当の12ケースを課題上の正解ラベルとして扱う。正解条件、判断理由、確認日はテストデータに固定し、検索結果から後付け生成しない。
