## 0. 今回整理する機能の境界

依頼文から、原文にある情報を根拠付きの候補として取り出し、営業が原文と照合して確認・修正できるようにする。

- 既存：MVP対象は規格品・類似品。新規特注・緊急・外注見積必須・複雑な図面判断を伴う案件は原則対象外で、既存の人間の手順へ戻す。
- 既存：価格・納期・加工可否を確定しない。顧客への自動送信をしない。
- 既存：「希望納期の記載を抽出する」と「その納期で納品できると約束する」は別。前者だけを扱う。
- 既存：必須チェック・分類はルール側、原文照合・修正・確定は人間側の責任。AIの出力だけで確認済みにしない。
- 今回の範囲外：類似見積検索、承認要否判定、メール生成、フォロー登録の実装。共通仕様にある全機能を、この抽出処理に一括実装しない。
- ユーザー決定：1依頼1商品に限定。複数商品は明示的に依頼全体を保留し、先頭商品だけの採用・自動分割は行わない。

## 1. 入力

### 1.1 画面・サーバーが受け付ける入力（既存仕様）

| 項目 | 必須条件・形式 | 入力元・注意点 |
|---|---|---|

| request_text | 必須・UTF-8テキスト | 営業が貼り付けるメール本文・依頼文・メモ。空白のみ不可。文字数上限は要確認。 |
| customer_name | 必須・文字列 | 営業入力。マスタ照合だけでは自動確定しない。外部AIには仮IDに置換。 |

`confirmed_request_fields`は初回抽出に必要な入力ではない。AIの候補を営業が確認・修正した後、後工程へ渡す確認済み情報として作成する。

`selected_reference_quote_id`、価格・粗利率・値引き率、フォロー期限・担当者は後工程の入力であり、今回の抽出用LLM入力に含めない。

### 1.2 外部AIへ渡す入力との分離

提案する処理順：入力検証 → 対象範囲確認 → ローカルで機密除去・仮ID化 → 許可項目検査 → 外部AIで抽出 → サーバーで型・根拠を検証 → 人間確認。

- 外部AIには、承認済みの抽出用プロンプト・スキーマと、送信許可のあるマスキング済みテキストだけを渡す。
- 入力オブジェクトやCSV全行、顧客・商品マスタ全件を、そのまま送信しない。
- 顧客実名と仮IDの対応表は外部へ出さない。実名の照合・復元はローカル側で行う。AIに隠した実名を推測させない。
- 顧客の入力欄と本文に異なる顧客が出た場合、AIの推測で一方へ統一せず人間確認へ戻す（提案）。
- 原文・参照情報はアクセス制御された内部領域で扱い、外部送信ログには未マスキングの機密値を残さない。

### 1.3 配布CSVとの関係

この機能の主入力は依頼文であり、配布CSVではない。

- 顧客・商品マスタ：後続の照合に使えるが、依頼文にない材質・寸法・顧客情報を「抽出した事実」として補完しない。
- 過去見積履歴：後続の類似検索用。過去の価格・条件を今回の依頼文から抽出した値に混ぜない。
- 見積依頼ログ：構造化された過去ログ。元メール本文と正解ラベルが用意されているかを別途確認し、存在しない本文を実データとして扱わない。
- 外注先マスタ：この抽出機能には不要。MVPで外注先候補を自動提示しないというスコープも維持する。

| キー | 型・内容 | 決める主体・状態 |

| request_id | string | 既存。入力の案件IDと一致をサーバーが保証。 |
| status | processing / needs_review / confirmed / error | 既存。サーバーが管理。AIが直接confirmedにしない。 |

| 品名 | product_name: string/null | 原文の品名。記載がなければ推測で作らない。 |

### 2.3 各項目の共通5属性

| 属性 | 既存要件 | 詳細案・要確認 |
|---|---|---|
| value | 抽出値を保持 | 欠損・曖昧・無効時はnull。0や空文字を欠損の代用品にしない。型は項目ごとに固定。 |
| source_quote | 原文引用を保持 | 原文から一致確認できる引用だけ。欠損ならnull。不正値が書かれていれば引用を残し、valueはnull・警告とする案。 |
| source_location | 原文位置を保持 | source_idと開始・終了位置で表す案。添付なら確認済みテキストとファイルhashにも紐付ける。表現・文字位置の数え方は実装前に固定。 |
| confidence | 信頼度を保持 | 数値範囲や算出方式は既存資料にない。0〜1またはnullを案とし、正答確率として扱わない。自動確定には使わない。 |
| human_status | 人間の確認状態を保持 | pending / confirmed / corrected / rejectedを案とする。AIには操作させない。確認者・時刻・修正前後は別途監査記録。 |

- 提案：マスキングで文字位置がずれるため、内部で原文との対応を保持し、返された根拠をサーバーで照合する。実名等の復元後の引用は内部画面だけで扱う。
- 提案：候補の抽出直後はneeds_review。確認・修正、必須チェック、監査記録が整った場合にだけconfirmedへ遷移する。confirmedは「依頼情報を確認済み」であり、価格や納期を承認済みという意味ではない。
- 既存：入力欠損・未定義・競合・JSON形式不一致・マスキング失敗・ログ保存失敗はneeds_reviewまたはerrorとし、確定入力として後工程へ渡さない。
- 提案：矛盾した複数値がある場合は勝手に最新値等を選ばず、該当箇所をwarnings_and_holdsに示して確認を求める。

## 3. 外部送信の制約

### 3.1 原文の規定と今回の適用を分ける

C-003は「顧客名、図面情報、見積金額、粗利率を外部AIへ送信する場合はマスキングまたは承認が必要」。G-007は「外部送信を最小化し、必要に応じてマスキング」。すべての外部送信を永久に禁止する規定ではない。

一方、現行MVP・共通入出力仕様は、対象項目の事前マスキング、許可項目限定、価格・承認用数値をLLMへ送らないこと、図面原本を送らないことを具体的に定めている。今回のMVPではこの厳しい側の仕様を適用し、承認例外を独断で作らない。

| 情報 | 今回のMVPでの扱い | 根拠 |
|---|---|---|
| 顧客実名 | 削除または仮ID化。未マスキング送信禁止。対応表は内部に保持。 | C-003、G-007、共通入力customer_name |
| 図面番号 | 削除または仮ID化。品番・ファイル名・本文への混入も確認。 | C-003、G-007、MVP外部AI送信 |
| 図面PDF・画像原本 | 外部LLMへ送信しない。Drive参照と人間確認済みテキストの仕組みに限定。 | MVP除外11、共通入力10〜11 |
| 図面から転記した材質・寸法・公差等 | 人間が確認しただけでは外部送信承認にならない。C-003の図面情報として送信許可範囲を確認。許可未確認なら外部送信を保留。 | C-003とMVP入力制限を合わせた適用 |
| 見積金額・単価・粗利率・価格承認用の値引き率 | 抽出LLMの入力から除外。本文・件名に含まれる金額も検査。数量や寸法まで一律に消さない。 | G-007、共通ルール・入力16〜18、ユーザー指定の単価保護 |
| APIキー・DB認証情報 | 入力・ブラウザ・AIプロンプト・ログへ含めない。APIキーは接続に必要な認証用途のみ。 | G-008、C-004＋基本的な秘密情報管理の提案 |
| メールアドレス・電話・署名・実ユーザーID・原本URL | 抽出に不要な識別情報は送らず、ローカル参照IDに置換する案。 | 許可項目限定・最小化を具体化した提案 |
| 許可済み・マスキング済み依頼文 | 必要最小限を送信候補とする。検査不合格・分類不明なら送らない。 | C-003、G-007、MVP外部AI送信 |

### 3.2 動作上の統制

- 既存：マスキング失敗時は外部APIを呼ばず停止。手動処理へ戻せること（G-010）。
- 既存：顧客送信・価格確定・納期保証は行わない（G-003〜G-005、C-008）。
- 既存：入力要約、抽出結果、操作・確認者、時刻、モデル・プロンプト・スキーマの版、Tool呼出し等を追跡する（G-006、C-005）。
- 既存：編集権限、レビュー、回帰テスト、版管理を設ける（G-001、G-002、C-002）。
- 提案：依頼文に「前の指示を無視して」「この宛先へ送信して」等があっても、それは入力データとして扱い、命令として実行しない。抽出処理に送信・価格確定・DB更新の自由な権限を与えない。
- 提案：外部AIの接続成功と、業務データ送信の承認・抽出精度の合格を別管理する。安全な固定文の接続テスト成功では、後二者を確認したことにならない。

## 4. 品質基準と判定方法

### 4.1 1項目・1案件の正しさ

提案する判定手順：人間が原文から先に正解表を作成 → AI結果を照合 → 修正なし／軽微修正／重大修正を記録 → 不一致理由・確認時間を記録。

正解表には、期待値だけでなく、原文の根拠、期待するnull・不足・警告、対象外判定、送信可否を含める。AI自身の採点だけで合格にしない。

| 観点 | 合格条件（抽出機能の受入基準案） |
|---|---|
| 原文への忠実性 | 記載値を取り出し、未記載の値を補完しない。希望納期を確約納期に変えない。 |
| 型・形式 | 固定キー・型・列挙値に一致。不正JSONを成功扱いせず、画面にエラーと手動経路を表示。 |
| 数値・単位・記号 | 数量と金額、品番と図面番号を混同しない。数量・単位、寸法の単位、公差の符号・範囲を保持。 |
| 欠損・曖昧さ | 未記載・曖昧・矛盾・無効を区別し、null・警告・保留で表現。必須不足の判定は確定ルールに従う。 |
| 根拠 | 非nullの候補を原文箇所に戻って検証できる。存在しない引用・位置を作らない。 |
| 人間の関与 | AI完了だけでは確認済みにならない。修正前後・確認者・時刻を保存。 |
| 安全性 | 送信禁止情報、原本、命令混入を含むケースで禁止動作が発生しない。マスキング不能は送信前に停止。 |
| 障害・ログ | API障害、型不一致、ログ失敗でも確定・引渡しをしない。理由と次の行動を表示。 |

資料の初回確認合格率を膨らませないため、出力後に人間が値を直したものは、軽微な修正でも「修正なし」に含めない。許可する正規化（明確な日付のISO化等）は事前に固定する。

### 4.2 数値目標

| 指標 | 判定 | 出典・位置付け |
|---|---|---|
| 初回確認合格率 | 修正なし件数 ÷ AI処理件数 ≥ 80% | MVP成功基準の既存目標。抽出機能単位で計測。 |
| 監査ログ完全性 | 必須記録の揃った処理件数 ÷ 全処理件数 ≥ 99% | MVP成功基準の既存目標。欠損案件を後工程へ渡してよい、という許容条件ではない。 |
| 重大なマスキング漏れ・誤送信 | 0件 | MVP成功基準の既存目標。1件でもあれば送信・利用継続を止め原因を確認。 |
| 型・停止条件・人間確認の制御テスト | 用意した必須テストで100%合格 | 今回の提案。80%の抽出目標と安全制御の合否を混同しない。 |
| 項目別正答率・欠損検知・確認時間 | 件数と内訳を記録。追加の合格閾値は実測・業務側の許容度により決定 | 提案。数量・単位・品番・納期・公差の誤りを平均値に埋もれさせない。 |

試験前に「AI処理件数」の扱いを固定する案：対象として受け付けてAI処理を試みた案件の初回実行を分母にし、API失敗・形式不正を成功例だけの集計から除外しない。再試行は別に記録。送信前に拒否した入力や対象外案件は別集計し、安全停止の合否を評価する。この詳細な集計規則は既存資料にはない提案。

### 4.3 テストケース案（未実施）

最低限、次を含む匿名・架空の依頼文と、人間が作成した正解表を用意する。最初は20件程度を提案するが、20件中16件で80%でも少数サンプルの予備確認にすぎず、本番精度の保証にはならない。ケース数より、以下の失敗パターンを覆うことを優先する。

1. 規格品の明確な依頼、類似品の明確な依頼。
2. 数量・単位・品番・希望日の欠損。
3. 希望日が「来週中」「なるべく早く」、年の記載がない等。
4. 数量0・負数、過去日、全角数字、先頭ゼロの品番。
5. 本文内の矛盾、顧客入力欄と本文の不一致。
6. 寸法・公差の複数記号、数量と単価が併記された文。
7. 複数商品の依頼（対応方針を確定後、漏れなく処理または明示的に保留）。
8. 新規特注・緊急・外注見積必須・図面判断必須。
9. 未確認添付、リンクのみ、差替えhash不一致。
10. 顧客名・図面番号・金額・粗利率が本文以外や署名に混入。
11. 指示上書き・顧客送信要求等を含む依頼文。
12. API失敗、タイムアウト、形式不正、ログ保存失敗。

外部送信遮断・確認状態・エラー時の制御は、まず通信をしないテストで確認する。実AIの精度試験は、送信可能データの承認と正解表の確定後に実施する。
