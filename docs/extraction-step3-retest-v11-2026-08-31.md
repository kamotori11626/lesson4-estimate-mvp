## 曖昧な例に残った課題

原文：

```text
検証用顧客Cです。前回同様のお見積りをお願いします。
品名: MCナイロンプレート300
数量: 1枚
希望納期: 来月半ば
寸法と公差は前回同様です。
```

1. 事前期待値の曖昧項目は寸法・公差・希望納期の3つ。実際は材質も加えた4つとなった。材質は本文に未記載なので、「情報不足」と「複数解釈がある」を混同している。
2. 寸法・公差にAMBIGUOUS警告は付くが、source_quote/source_locationがnull。「寸法と公差は前回同様です。」という根拠を表示できていない。
3. 納期には「来月半ば」の正しい引用があり、具体的な日付を推測していない。品名・数量・単位も保持され、前回のSCOPE_UNCERTAINは発生していない。
4. 引用が存在した箇所は3例合計16件とも原文位置に一致。ただし、引用が欠けた寸法・公差の妥当性が確認できたという意味ではない。

確認した実装上の原因：`normalizeResult` は `proposed.ambiguous` がtrueなら、原文引用があるかを必須条件にせず曖昧警告を作る。そのため、根拠なしの警告も残る。モデルがなぜ材質を曖昧扱いしたかは、生応答や内部判断理由を保存していないため断定しない。

このターンは再検証と対処方針の助言が対象。判定条件を緩めて合格扱いにしたり、アプリを追加修正して再送したりしていない。

## 教材の例に加えて明文化すべき対処方針

以下は現在のMVPに対する助言。教材に追加でそう書かれているという意味ではなく、この再検証でアプリに追加実装したわけでもない。

| 状況 | 対処方針 | 現状・優先度 |
|---|---|---|
| 未記載と曖昧を混同 | 未記載はnull＋情報不足。記述があるが確定できないならnull＋原文引用＋具体的な要確認理由。原文の記載を見つけられない状態も、断定的な「曖昧」と分ける | 最優先。今回の材質警告と引用欠落を修正対象にする |
| 一部項目だけ不明 | 明確な別項目は候補として保持。未確認項目は確定しない | 今回改善を確認。実務での汎用性は別途検証 |
| 複数商品／商品数不明 | 依頼全体を保留し、最初の商品だけ取り出さない。人間の確認へ戻す | 既存の安全境界を維持 |
| 同じ項目に矛盾・訂正がある | 「100個」と「200個」などを無根拠に選択しない。両方の記載箇所と訂正関係を提示し、承認された優先ルールがなければ確認に回す | 部分対応。現在は複数数量を全体保留するが、矛盾／訂正専用の整理は未実装 |
| 不正な値・単位不明 | 数量0/負数、存在しない日付等は採用しない。数量と単位を一緒に確認し、0埋めや単位の推測をしない | 数量・日付の検査は既存。項目別の妥当性・単位ルールは必要範囲を業務側と定義 |
| 原文に根拠がない候補・警告 | 値だけでなく警告にも原文根拠を要求。根拠なしは「要確認理由を検証できない」とし、正しい曖昧判定として採用しない | 値の根拠検査は既存。警告の根拠検査が不足している |
| 機密・未許可データ、業務範囲外 | 外部送信前に止める。情報抽出以外の価格確定・納期保証・加工可否・顧客送信をしない | 現在は固定匿名サンプルだけを許可し、範囲を拡大しない |
| API障害・不正JSON・保存失敗 | 業務上の情報不足とシステム失敗を分ける。失敗を成功扱いせず、エラー理由と手動復帰先を示す | 既存の停止・再試行なしを維持 |

「最も可能性が高い候補を提示」は対処方針の一例であり、必ず1つに絞る必要はない。今回のような見積情報では、根拠が弱い候補を高信頼度というだけで選ぶと誤発注・納期誤認につながる。根拠のある候補が複数なら併記、根拠がなければ候補を作らず要確認とすることを勧める。「来月半ば」を勝手に15日とする処理は採用しない。

最後に、要確認になった後の担当者・確認事項・後工程へ進める条件も定義が必要。例えば営業が原文・顧客回答を確認し、必要に応じて技術担当へ引き継ぐ案があるが、担当・必須項目・承認条件は業務側の合意が必要。現段階の全出力は未確認下書きであり、確認済み扱いにはしない。
