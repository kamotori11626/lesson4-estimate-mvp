# 承認要否判定 + メール案作成 Step 1 要件整理

作成日：2026-09-03

## 1. 要件整理の根拠

- TECH::MASTER「承認要否判定 + メール案作成」（curriculum 15330）の全本文
- `役割分担表.txt` の Step 12〜19およびルールエンジンの共通設計原則
- `共通入出力仕様.txt` の入力・出力・操作記録・エラー時動作
- `アーキテクチャ意思決定メモ.txt` の人間とAIの責任境界、変更管理、監査要件
- `MVPスコープ定義書.txt` の承認判定・メール案作成・MVP対象外
- `AIに任せない判断一覧.txt` の価格・納期・顧客送信に関する責任境界
- `17_文書棚卸し` の承認基準（「20%未満」と「18%未満」の矛盾）
- `28_ガバナンス要件.csv` の G-001〜G-010。教材の訂正に従い、セキュリティ、運用、ガバナンスに関する制約事項の正本として直接参照する
- `26_技術運用制約.csv` の C-001〜C-010。利用者環境、外部AI利用、DB接続、ログ・監査、既存システム連携等の実装上の補足制約として直接参照する
- Chapter 3の実装済み `extraction-1.0` とChapter 4の類似案件検索・価格差異判定

この機能の目的は、価格や承認結果をシステムが確定することではない。ルールエンジンが承認要否の候補・承認者候補・根拠を再現可能な形で提示し、AIが確認用メールの下書きを生成して、人間が判断・修正・送信できる状態を作ることである。

## 2. 対象範囲と責任境界

### MVPで行うこと

- 定義済みルールによる `required`／`not_required`／`hold` の候補判定
- 適用ルールID・版、入力値、理由、承認者候補の表示・保存
- 顧客への不足情報問い合わせ、技術・購買への社内確認、見積送信の各メール案作成
- 人間による下書きの修正・採用・却下理由の保存

### MVPで行わないこと

- 価格・値引き・納期の最終決定（G-003、G-004）
- 管理職による実際の承認・却下操作を代行すること
- 顧客または社内へのメール自動送信（G-005）
- 新規特注・緊急案件の自動処理。これらは既定のMVP対象外として手動運用へ戻す

`required` は「正式承認が完了した」という意味ではなく、「既存手順で管理職承認を取得すべき候補」である。正式結果は人間が既存手順で判断し、結果を手動登録する。

## 3. 入力要件

### Chapter 3の情報抽出機能の保存記録から受け取るもの

| 入力 | 使用目的 | 受入条件 |
|---|---|---|
| `request_id`、`schema_version`、`audit_log_id` | 案件・版・操作記録の関連付け | 空欄、版不一致、ログ保存不可は処理停止 |
| `status`、`extracted_fields` | 確認済み依頼事実を文面へ反映 | AI抽出直後の値ではなく、人間が照合・修正した現在値だけを使う |
| `missing_fields` | 顧客への問い合わせ項目を決める | 項目ID・理由・重要度が必要。同じ項目を重複させない |
| `warnings_and_holds` | 判定停止、確認事項、禁止処理の制御 | `hold` が1件でも残る間は見積送信案を完成扱いにしない |
| `item_scope` | 1依頼1商品制限の確認 | `single` 以外は承認判定へ進めず、手動分割または保留 |
| `case_type` | MVP対象判定、確認先の補助 | 規格品・類似品だけ対象。新規特注・緊急は手動運用 |
| `required_tech_review`、`required_supplier_quote` | 社内確認文面の宛先と確認事項 | 真偽値と根拠が必要。欠損・競合時は経路判定を保留 |

現行のChapter 3固定出力には `case_type`、`item_scope`、`required_tech_review`、`required_supplier_quote` がトップレベル項目として揃っていない。Step 2では既存の抽出結果・保存記録から安全に導出するか、中間入力スキーマとして明示的に追加する必要がある。推測で値を埋めてはならない。

### Chapter 4の類似案件検索から受け取るもの

| 入力 | 使用目的 | 受入条件 |
|---|---|---|
| `similar_quotes` | 根拠・差異・注意事項の表示 | 顧客名、過去価格、粗利率等は外部LLMへ送信しない |
| `selected_quote_result` | 人間が採用した参照見積と理由を確認 | 未選択・未確認は価格確定の根拠にしない |
| `price_analysis` | 価格差異による停止・確認要否を判断 | ルール版、比較可否、重大度、差額・差率、重要注記が必要 |

### 営業が確認して入力するもの

Chapter 3・4の出力だけでは、価格承認に必要な数値は揃わない。次を別入力として必須化する。

| 入力 | 型・検証 | 外部LLMへの送信 |
|---|---|---|
| `planned_price` | 0より大きい円の整数 | 禁止 |
| `cost` | 0以上の円の整数。`planned_price` とともに粗利率をサーバー側で再計算 | 禁止 |
| `list_price` | 0より大きい円の整数。`planned_price` とともに値引率をサーバー側で再計算 | 禁止 |
| `human_approval_result`（後続実装） | 承認／差戻し／却下、承認者、理由、時刻 | 禁止。既存手順の結果を登録するだけ |

数値の欠損、再計算不一致、入力根拠欠損は `not_required` にせず `hold` とする。

## 4. 承認ルール一覧

### 採用する判定方式

- 承認要否は外部AIではなくローカルのルールエンジンで判定する。
- 判定ごとにルールID、版、入力値、結果、理由、承認者候補、実行時刻を保存する。
- 複数ルールが該当する場合は、`hold`、`required`、`not_required` の順に安全側を優先する。
- ルール未定義、入力欠損、計算不一致、ルール競合は `hold` とし、人間確認へ戻す。
- ルール変更はG-002に従い、責任者レビュー、承認、回帰テスト、版更新後に反映する。

### MVPルール

| ルールID（案） | 条件 | 出力候補 | 承認者・次の行動 | 根拠・状態 |
|---|---|---|---|---|
| `APR-INPUT-001` | 見積金額・粗利率・値引き率の欠損、範囲外、再計算不一致、根拠欠損 | `hold` | 営業が原価・定価・提示価格を再確認 | 共通入出力仕様。確定ルール |
| `APR-SCOPE-001` | 1依頼複数商品、商品数不明、新規特注、緊急 | `hold`（MVP対象外） | 営業が手動分割または既存手順へ切替 | MVPスコープ定義。確定ルール |
| `APR-GM-001` | 粗利率 `< 18%` | `required` | 管理職候補へ既存手順で承認依頼 | 18%ルールと20%ルールの双方で承認対象となる範囲 |
| `APR-GM-002` | 粗利率 `18%以上20%未満` | `hold` | 管理職が正式基準を決定するまで自動判定しない | `17_文書棚卸し` に18%と20%の矛盾。未解決 |
| `APR-GM-003` | 粗利率 `20%以上` | 粗利率ルール単独では非該当 | 他ルールを評価 | 両文書で粗利率基準の承認対象外 |
| `APR-DISCOUNT-001` | 値引き率 `> 0` だが正式な承認閾値・例外が未登録 | `hold` | 管理職が閾値、顧客別例外、レビュー帯を決定 | 閾値の根拠なし。未解決 |
| `APR-PRICE-DIFF-001` | Chapter 4の価格差異判定が `stop` | `hold` | 営業が差異根拠を確認し、管理職候補へ確認 | 既存の `price-difference-rules-1.0`。正式承認ルール化はG-002レビュー前 |
| `APR-RULE-001` | ルール版不一致、競合、未定義条件 | `hold` | 管理職・情シス／FDEがルールを確認 | G-002、G-009、G-010 |
| `APR-NONE-001` | 対象範囲内、入力有効、保留なし、どの承認ルールにも非該当 | `not_required` | 営業が次工程へ。UIでは警告理由を表示しない | 教材の通常ケース。ただし監査ログには「該当ルールなし」を記録 |

`18%以上20%未満` を勝手に `required` または `not_required` にすると、どちらかの既存文書へ必ず違反する。よってStep 1では `hold` が唯一説明可能な処理である。

値引き率は、教材に「判断材料」として示されているだけで、正式な閾値が確認できない。任意の10%等を実装してはならない。正式閾値が決まるまでは、値引きなしだけを非該当とし、値引きありは保留する。

粗利率・値引き率の承認基準は、技術選定ではなく東和精密部品株式会社の採算方針・権限設計に属する。したがって、最終決定者は営業部長・経営管理等の業務責任者とし、FDEは次を担当する。

- 矛盾・未定義部分と、各案が承認件数・管理職負担・低採算リスクへ与える影響を示す。
- 決定者、決定日、適用開始日、例外、ルールID・版を記録する。
- 決定済みルールだけを実装し、境界値・例外・競合ケースを回帰テストする。
- 正式決定前の範囲を推測で自動判定せず、`hold` として管理職確認へ戻す。

値引き率については一律閾値だけでなく、定価の定義、顧客別の承認済み値引き条件、案件種別、期間限定条件、例外承認者を業務責任者が定める必要がある。顧客別条件の正本と有効期間が確認できない限り、自動適用しない。

## 5. 文面の種類

共通入出力仕様に合わせ、トップレベルの文面種類を次の3つに固定する。

| 出力キー | 宛先・目的 | 生成条件 | 人間の関与 |
|---|---|---|---|
| `customer_inquiry_draft` | 顧客へ不足・曖昧情報を確認 | `missing_fields` に顧客確認項目が1件以上 | AIが案を生成 → 営業が原文・宛先・確認事項を照合し、修正して既存メールで送信 |
| `internal_review_draft` | 技術見積または購買へ仕様・加工・外注条件を確認 | 技術確認または仕入見積フラグがtrue、もしくは重大な仕様差 | AIが案を生成 → 営業が相手と質問を確認し、技術／購買が判断して回答 |
| `quote_email_draft` | 顧客へ確認済み見積書を送るための本文案 | 必須項目確認済み、保留なし、必要な人間承認結果が登録済み | AIが案を生成 → 営業が価格・納期・宛先・添付を確認し、手動送信 |

管理職への承認依頼メールは、現行の共通入出力仕様に独立した出力キーがないためStep 1では追加しない。承認要否と理由を画面表示し、既存の承認手順を使う。

## 6. AIへ渡す文面生成入力

AIへ渡すのは、匿名の導入文と結び文を生成するための、最小化した構造化入力だけとする。

- 文面種類、宛先の役割（顧客／技術／購買）
- 文面の目的、匿名の導入文・結び文という出力種別
- 不足項目と追加質問の件数（項目名・質問本文は含めない）
- 禁止表現、文体、出力JSONスキーマ、モデル版、プロンプト版

顧客名、商品名、品番、案件番号、顧客向け問い合わせ番号・元メール件名、自社担当者名、不足項目名、追加質問本文、図面番号、見積金額、原価、粗利率、実在する宛先、依頼原文、メールアドレス、添付原本は送らない。AIにはプレースホルダーや必須項目の生成も任せない。AI応答後、顧客名・商品情報・弊社案件番号・顧客向け問い合わせ番号または元メール件名・担当者・不足項目・追加質問および顧客確認メールの必須2文を、サーバー側の固定処理で組み込む。顧客向け問い合わせ番号・元メール件名は元依頼と照合した人間の入力を必須とし、内部UUIDだけを顧客識別情報として扱わない。承認判定の入力値・結果と価格差異の実額もAIへ送らない。

## 7. 文面の制約

### 教材が定める絶対的な制約

1. **価格を断定しない**
   - 「○○円でご提供します」「この価格で確定しました」等を生成しない。
   - 価格確認前は「正式な見積は改めてご連絡いたします」等、確認中であることを明示する。
2. **納期を確約しない**
   - 製造・技術・購買の確認前に「○月○日までに納品いたします」「必ず納品します」等を生成しない。
   - 未確認時は「納期については確認の上、改めてご連絡いたします」等とする。
3. **自動送信しない**
   - 生成文面は必ず「下書き」として表示する。
   - 営業が宛先・本文・事実・添付を確認し、必要な修正をした後、既存メールから手動送信する。MVPには顧客または社内へのメール送信機能を実装しない。

### 禁止する内容

- AIが価格・値引き・納期・加工可否・承認結果を確定したように書くこと
- 「この価格で確定しました」「必ず納品します」「承認済みです」等を、確認済み根拠なしに出力すること
- 原文や確認済みデータにない仕様、日付、数値、宛名、添付ファイルを補完すること
- 顧客向け文面へ社内の粗利率、原価、承認基準、内部コメントを含めること
- 顧客向けと社内向けの文面を取り違えること
- 下書き生成後に送信APIやメール画面の送信操作を自動実行すること

### 必須の安全動作

- 不足項目を推測せず、具体的な質問へ変換する。
- 希望納期は顧客希望として書き、製造・納品の確約と混同しない。
- 添付は存在が確認されたファイルだけをチェックリストへ載せる。
- 下書き生成失敗、JSON不一致、禁止表現検知、マスキング失敗、ログ保存失敗時は文面を完成扱いにせず、テンプレートによる手動作成へ戻す（G-010）。
- 表示画面には必ず「下書き」「人間確認前」「自動送信されない」を明示する。

## 8. 文面の品質基準

| 基準 | 合格条件 | 確認方法 |
|---|---|---|
| 禁止表現の不在 | 価格断定、納期確約、AIによる承認済み宣言が0件 | ローカルの禁止表現・文脈ルールで検査した後、営業が本文を確認する。単純なキーワード一致だけでなく、「見積金額を確認したい」のような許容表現との文脈差を確認する |
| 情報の正確性 | 顧客名、案件番号、品目、数量、材質、確認状況、日付、添付等の記載が、確認済み抽出結果・人間の修正・存在確認済み添付と一致する。根拠のない補完が0件 | 文面中の事実を入力項目・参照IDへ対応付け、営業が原文と照合する |
| 宛先の適切性 | 顧客向け、技術向け、購買向けの文面種類が一致し、顧客向け文面に粗利率・原価・承認基準・社内コメントが含まれない | `draft_type` と `recipient_role` の組合せをルール検査し、営業が宛先と内容を確認する |
| 不足情報の網羅 | 顧客または社内へ確認すべき対象の `missing_fields`／質問IDが、重複なくすべて文面に含まれる。対象外の質問が追加されていない | 入力した確認項目ID集合と、文面が参照した項目ID集合の一致を自動検査する |
| 敬語・文体の適切さ | 簡潔で失礼のないビジネスメールであり、顧客向けは社外敬語、社内向けは役割に応じた依頼表現になっている | AIの固定プロンプトで文体を指定し、最終的には営業が読みやすさ・敬語・過不足を確認する |

5基準のうち1つでも不合格なら `human_review_status=pending` のまま完成扱いにせず、再生成または人間の修正へ戻す。自動検査に合格しても、人間確認を省略して送信してはならない。

## 9. 出力スキーマ

### 承認要否判定

共通入出力仕様のトップレベルキー `approval_requirement` を変更せず、次の構造へ固定する。複数ルールが該当した場合、`rule_id` には最終結果を決めた優先ルールを記録し、その他の適用ルールは監査ログと `warnings_and_holds` に残す。

```json
{
  "approval_requirement": {
    "status": "required | not_required | hold",
    "approver_role": "管理職 | null",
    "rule_id": "APR-GM-001",
    "rule_version": "approval-rules-0.1-draft",
    "input_values": {
      "planned_price": 0,
      "cost": 0,
      "list_price": 0
    },
    "calculated_values": {
      "gross_margin_rate": 0,
      "discount_rate": 0
    },
    "reason": "適用条件と根拠"
  }
}
```

画面へ金額・率を表示できるのは権限のある利用者だけとし、外部LLMにはこのオブジェクトを渡さない。`not_required` の場合、画面では警告理由を表示せず、監査ログに適用ルールなしを残す。

### メール案

共通入出力仕様の `customer_inquiry_draft`、`internal_review_draft`、`quote_email_draft` を維持する。下記は顧客問い合わせ案の例であり、社内確認案・見積送信案も同じ監査項目を持つ。

```json
{
  "customer_inquiry_draft": {
    "subject": "下書き件名",
    "body": "下書き本文",
    "recipient_role": "customer",
    "referenced_item_ids": ["missing-field-id"],
    "attachment_checklist": [],
    "prohibited_expression_check": {
      "passed": true,
      "findings": []
    },
    "human_review_status": "pending",
    "auto_send": false
  }
}
```

未知のキー、列挙値違反、参照項目ID不一致は受け付けず、再生成または手動テンプレートへ戻す。

## 10. ログ要件

案件ID・実行IDを共通キーとして、次を追跡する。

- 入力版、データ版、ルールID・版・優先度
- 承認判定へ使った入力値、適用ルール、結果、理由、保留理由
- AIへ送った項目名、マスキング検査結果、送信可否。ログにも未マスキング値を残さない
- 生成文面、参照項目ID、モデル・プロンプト版、禁止表現検査
- 人間による修正前後、採用・却下、確認者、確認時刻
- 既存手順での承認結果と人間の理由
- 障害、フォールバック理由、手動運用への切替

現行アプリには正式なWeb認証がないため、現段階の確認者名は自己申告であり「認証済み利用者」とはみなせない。本番相当の承認・監査と称するには、認証と権限制御が別途必要である。

## 11. Step 2へ進む前の未決事項

| 優先度 | 未決事項 | 決める人 | 未決のまま実装する場合の安全動作 |
|---|---|---|---|
| 最優先 | 粗利率の承認基準を18%未満か20%未満のどちらへ統一するか | 東和精密部品株式会社の営業部長・経営管理等の業務責任者 | `<18%` は承認候補、`18%以上20%未満` は保留 |
| 最優先 | 値引き率の基準となる定価、承認閾値、顧客別例外、有効期間、境界のレビュー帯 | 東和精密部品株式会社の営業部長・経営管理等の業務責任者 | 値引きなし以外は保留。未承認の顧客別条件は自動適用しない |
| 高 | 価格差異 `stop` を正式な管理職承認ルールにするか | 管理職、FDE／情シス | 停止・管理職確認候補として表示し、正式承認完了とは扱わない |
| 高 | 現行抽出結果から案件種別・技術確認・仕入見積フラグをどう受け渡すか | FDE、営業、技術、購買 | 欠損時は経路判定を保留 |
| 高 | メール案へローカル差し込みしてよい実値と、送信前の権限 | 情シス、営業管理職 | 実値の自動差し込みを無効化し、営業が画面上で確認入力 |

Step 2では、未決の業務ルールを仮の数値で埋めず、上記の安全動作を自動テストの期待値として実装する。

## 12. Step 1の完了条件

- 承認ルールの確定部分と未決部分を分離した。
- Chapter 3・4から受け取る入力と、営業が追加確認する入力を分離した。
- 文面種類を共通入出力仕様の3種類に固定した。
- 価格・納期・承認・送信の責任を人間へ残した。
- 教材の絶対的な制約3点と文面品質基準5点を、確認方法を含めて明文化した。
- 機密情報を承認ルール内のローカル処理と、匿名化した文面生成入力に分離した。
- 未決・欠損・競合・外部AI障害・ログ障害時の保留／手動経路を定義した。

以上により、Step 1の要件整理は完了とする。ただし、未決の承認閾値があるため、Step 2で実装できるのは「確定済み条件の判定」と「未決条件の安全な保留」までである。
