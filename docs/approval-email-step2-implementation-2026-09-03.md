# 承認要否判定 + メール案作成 Step 2 実装記録

作成日：2026-09-03

## 1. 教材の依頼ポイントとの対応

| 教材のポイント | 実装内容 |
|---|---|
| 承認ルールを具体的に列挙 | `approval-rules-0.1-draft` として、対象外、入力不足、粗利率、値引率、価格比較不能、技術確認、外注確認を別IDで実装 |
| 入力条件と判定結果のペア | 各ルールが `required`、`not_required`、`hold` を返し、`hold` を最優先に集約 |
| 判定理由を含める | 再計算値、閾値、保留理由、確認先を画面・API・DBへ記録 |
| 文面の種類と目的 | 顧客への不足情報確認、社内への確認依頼、顧客への見積回答予告の3種類に固定 |
| 禁止表現を明示 | 価格断定、納期確約、未確認の承認済み・製造可否・添付、顧客向け社内情報をローカル検査 |
| 含める情報を指定 | 文面種類、役割、不足項目ID・一般名、追加質問、ローカル差込み用の顧客・商品・案件・担当者 |
| 文面例を示す | 3種類のローカル定型文を実装し、Gemini障害時も利用可能にした |

## 2. 承認判定の実装

- 判定はNode.js上のローカル固定ルールで実行し、Geminiは使用しない。
- 予定見積金額・原価・基準価格を整数円で受け取り、粗利率と値引率はサーバー側で再計算する。
- 粗利率は `<18%` を `required`、`18%以上20%未満` を `hold`、`20%以上` を粗利率単独では非該当とする。
- 値引率は `0%` を非該当、`0%超` を正式閾値決定まで `hold` とする。
- 数値欠損・範囲外、未確定項目、MVP対象外、価格比較不能は `not_required` にせず `hold` とする。
- 抽出結果の原文照合・修正下書きが一度も保存されていない案件は `hold` とし、AI抽出直後の値をそのまま後工程へ流さない。
- 技術確認・外注見積が必要な場合は理由を必須にし、技術担当または購買・外注担当を返す。
- ルールID・版、全ルール結果、入力値、再計算値、最終状態をDBへ保存する。

閾値は技術上の正解ではなく、東和精密部品株式会社の業務責任者が決める。現在の18%・20%と値引率の扱いは、安全に開発を進めるための暫定処理であり、正式承認ルールではない。

## 3. メール下書きの実装

- 初期方式は外部送信のないローカル定型文とした。
- Gemini方式も用意したが、画面で匿名・最小化データを表示し、都度同意した場合だけ1回送信する。自動再試行しない。
- Geminiへ送るのは文面種類、目的、宛先の役割、匿名の導入文・結び文という出力種別、不足項目数・追加質問数、禁止事項だけである。
- 顧客名、商品名、品番、案件番号、顧客向け問い合わせ番号・元メール件名、担当者名、不足項目名、図面番号、価格、原価、依頼原文、メールアドレス、追加質問本文は送らない。
- Geminiにはプレースホルダーを要求しない。実値、不足項目、追加質問および顧客確認メールの必須2文は、Gemini応答後にサーバー側の固定処理で組み込む。
- 顧客名・品番・品名・案件ID・不足項目はブラウザから受け取った値を信用せず、関連する抽出記録をサーバー側で再読込する。
- 顧客向け文面では、顧客が認識できる問い合わせ番号または元メール件名の入力を必須とし、未入力ならGemini送信前に停止する。この値はローカルで本文へ挿入し、Geminiへ送らない。
- 顧客問い合わせは不足項目または質問がある場合だけ、見積回答予告は承認判定が `not_required` の場合だけ作成できる。
- 出力は件名、本文、参照した不足項目IDの固定JSONとする。未知項目、欠落、存在しない項目IDは拒否する。
- 生成直後と、人間が編集して採用記録する直前の2回、禁止表現・不足項目・入力値との対応・宛先・長さを検査する。
- 下書きの採用・却下、理由、自己申告の記録者、日時をDBへ保存する。
- メール送信ボタンも送信APIも実装していない。

## 4. DBと監査

既存CSV・抽出・類似検索テーブルを変更せず、次の追加テーブルを作成した。

- `approval_email_runs`：承認判定入力、結果、ルール版
- `approval_email_drafts`：生成方式、外部送信プレビュー、生成前入力、文面、品質検査、人間の判断
- `approval_email_events`：判定、下書き生成、人間確認の操作履歴

現行UIには本人認証がないため、記録者名は自己申告である。正式な承認記録や本番監査とは呼ばない。

## 5. 検証結果

- 全自動テスト：160件中160件合格（実Gemini呼出しなし）
- 粗利率境界：20%=`not_required`、19%=`hold`、17%=`required` をローカルAPI・DBで確認
- 不足4項目がある案件：粗利率30%・値引率0%でも `hold` を確認
- ローカル下書き：不足項目4件と追加質問を含み、機械検査合格、DB保存を確認
- 編集後の禁止表現：「10,000円でご提供」「明日納品」を価格断定・納期確約として採用拒否
- 通常Chrome画面：承認判定欄、理由、全ルール、3文面種類、下書き表示、送信機能なしを確認
- 顧客確認文：顧客名・商品情報・弊社案件番号・顧客向け問い合わせ番号または元メール件名・自社担当者、不足4項目、顧客への依頼文、回答後の自社対応文をサーバー側で組み込み、機械検査合格とDB保存を確認
- Gemini模擬応答：プレースホルダーや必須文を返さない匿名の導入文・結び文だけでも、ローカル合成後の完成文が機械検査に合格することを確認
- 実送信前プレビューはサーバーが作成し、画面表示と実送信予定JSONを同一にした。同意前は生成ボタンを無効化する
- このStep 2では実Gemini送信を行っていない。実AIの文面品質はStep 3のテスト対象である。
